# Issue Analysis — Batch #15071 / #15072 / #15073 / #15078

## Bug #15071 — "[Onboarding] 'Enable Introscreen' toggle has no effect"

**State:** In Progress  
**Assigned to:** Vedat Kökmen  
**Iteration:** Sprint EUM 2601  
**Severity:** 3 - Medium | **Priority:** 2

**Problem summary**  
The "Enable Introscreen" toggle in Onboarding general settings does not control whether the welcome screen appears in the guest onboarding wizard. The toggle is expected to show/hide the welcome screen, but the portal always shows the intro screen regardless of the toggle state.

**Repro steps**
1. In EUM, open Configuration → ONBOARDING → General settings
2. Turn ON "Enable custom onboarding process" (activates the organization portal)
3. Turn OFF "Enable Introscreen"
4. Approve a pending guest request and open the onboarding link as the guest
5. Pass the PIN gate
6. Observe the first wizard page

**Expected behavior**  
With "Enable Introscreen" OFF, the onboarding wizard starts directly on the Invitation step (no welcome screen). With it ON, the welcome screen is shown first.

**Actual behavior**  
The welcome screen is always shown; the toggle has no observable effect.

**Suspected scope**  
Full-stack (backend config delivery + frontend portal integration). The setting exists in the database/config, but either: (a) the backend is not including the setting in the portal config payload, or (b) the frontend portal is hard-coding the intro screen ON and ignoring the setting.

**Ambiguities / missing info**  
- Bug notes mention the portal hard-codes the intro screen ON and the setting is not part of the portal config payload per spec `onboarding-portal-wizard.md` open question OQ-2. This suggests a known design decision that may need clarification: is the toggle expected to control the portal intro, or is that a future feature?
- Attachment: `bug1-bug2-settings-overview-introscreen-on-logo-delete.png` (screenshot showing settings overview)

**Related work item:** #14170

## Bug #15073 — "[Onboarding] No feedback when uploading a logo larger than 2 MB"

**State:** In Progress  
**Assigned to:** Vedat Kökmen  
**Iteration:** Sprint EUM 2601  
**Severity:** 4 - Low | **Priority:** 2

**Problem summary**  
When a user attempts to upload a company logo larger than the stated 2 MB limit, the file is silently rejected with no error message displayed. The user cannot tell why the logo did not appear. The Classic app showed an inline error in this case.

**Repro steps**
1. Configuration → ONBOARDING → General settings, custom onboarding ON
2. Under "Your company logo", click "Upload" and select an image larger than 2 MB
3. Observe: no logo appears and no message is shown

**Expected behavior**  
An error message informs the user that the file exceeds the 2 MB limit; the file is not uploaded.

**Actual behavior**  
Nothing happens. The file is discarded without any message.

**Suspected scope**  
Frontend (validation and error feedback). The file-size check likely exists on the backend or client-side, but the error is not surfaced to the user. An error toast, inline message, or validation message is missing.

**Ambiguities / missing info**  
- Code note mentions the file-size check "silently returns without any user notification" — confirm whether the check is happening on the client (early rejection) or server (silent discard).

**Related work item:** #14170

## Bug #15078 — "[Onboarding] Logo upload/delete is slow to reflect on screen"

**State:** In Progress  
**Assigned to:** Vedat Kökmen  
**Iteration:** Sprint EUM 2601  
**Severity:** 4 - Low | **Priority:** 2

**Problem summary**  
Uploading or deleting the company logo results in a visible 1–2 second delay before the UI reflects the change. In the Classic app, the change was instant. This is a perceived performance regression and suggests the UI is waiting for the backend save operation to complete before updating the preview.

**Repro steps**
1. Configuration → ONBOARDING → General settings, custom onboarding ON
2. Upload a logo under 2 MB; observe the delay before the preview renders (~1.5–2 s)
3. Click "Delete"; observe the delay before the preview disappears (~1–1.5 s)

**Expected behavior**  
The logo preview appears/disappears immediately on upload/delete (as in the Classic app), with the save happening in the background (optimistic update).

**Actual behavior**  
The UI updates only after a 1–2 second delay per action.

**Suspected scope**  
Frontend (UX/performance optimization). This likely requires implementing optimistic UI updates (show preview immediately, save in the background, rollback if the save fails).

**Ambiguities / missing info**  
- Confirmation that the delay is from the backend round-trip time, not a client-side processing issue.

**Related work item:** #14170
